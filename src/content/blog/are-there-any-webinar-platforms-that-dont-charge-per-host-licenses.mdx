### The Problem with Per-Host Licensing

1. **Credential Sharing & Security Risks:** When licenses cost anywhere from $40 to $300+ per host per month, teams routinely share generic logins (e.g., `marketing@company.com`). 4. **Misaligned Value Metrics:** A host seat delivers zero intrinsic value if no audience attends. Companies end up paying for idle software capacity simply to maintain administrative access for occasional presenters.

## Core Economic Models: How "No Per-Host" Pricing Works

When evaluating **webinar platforms with no per-host license**, software buyers encounter three alternative monetization frameworks:

### 1. Attendee-Capacity Pricing (Room-Based)
Under this model, the software tier is defined solely by the maximum number of live, concurrent attendees who can join a session at any given moment (e.g., up to 250 attendees, up to 1,000 attendees). 

* **How host seats work:** Your account can have 5, 50, or 500 team members with full administrative privileges. They can schedule and run events independently, provided the live audience in any single event does not exceed the contracted room threshold.
* **Best suited for:** High-frequency marketing teams where multiple team members run localized, mid-sized events simultaneously.

### 2. Registration / Usage-Based Pricing
This framework decouples pricing from live concurrency, charging instead on the aggregate volume of registered users or active published webinar funnels over a monthly billing cycle.

* **How host seats work:** Administrative access is fully democratized. You pay for audience demand and workflow throughput rather than internal users.
* **Best suited for:** Asynchronous sales funnels, evergreen education, and continuous customer training programs where content is pre-recorded and automated.

### 3. Credit-Based / Streaming-Hour Models
Some platforms apply a hybrid model combining attendee room limits with aggregate monthly broadcast hours (e.g., 20 live broadcast hours per month with a 100-person room).

* **How host seats work:** Anyone on the team can consume those hours to host webinars without individual licensing overhead.
* **Best suited for:** Fast-moving startups and agencies running intensive, episodic campaigns across multiple distinct brand accounts.

### The Technical Evolution: From Provisioned SFU Compute to Dynamic Edge Streaming

To understand why legacy vendors still demand per-host licenses, you must understand the infrastructure limitations of late-2000s WebRTC and video routing architecture.

```
LEGACY INFRASTRUCTURE (Tied to Host Account)
[Named Host ID] ---> [Dedicated MCU/SFU Server Instance] ---> [Fixed Bandwidth Allocation]
(High idle cost per registered user, regardless of broadcast status)

MODERN SERVERLESS INFRASTRUCTURE (Decoupled & Ephemeral)
[Any Authenticated User] 
       │
       ▼
[Edge Ingest (WHIP/WHEP)] ──> [Dynamic WebRTC SFU Mesh] ──> [HLS / Low-Latency CDN] ──> [Audience]
(Zero idle compute cost; resources scale only during active transmissions)
```

#### 1. Legacy Monolithic Architectures (MCU/SFU Binding)
Early enterprise video tools (Cisco Webex, GoToWebinar, and original Zoom topologies) provisioned static, persistent media-routing pipelines tied directly to a specific user's identity. In an MCU (Multipoint Control Unit) or legacy SFU (Selective Forwarding Unit) deployment, provisioning a "host" meant reserving server-side mixing resources, database instances, and dedicated recording buffers for that credential. Vendors passed this fixed operational cost directly to the buyer as a "named seat."

#### 2. Modern Edge-Routed Infrastructure (WHIP, WHEP, and Decoupled Ingest)
Modern **webinar platforms with no per-host license** treat video streams as ephemeral data payloads rather than persistent identity assets. 
* **Ingest Protocol**: Presenters connect via WebRTC-HTTP Ingestion Protocol (WHIP) or secure RTMP directly to the nearest global Point of Presence (PoP).
* **Dynamic Media Pipelines**: Server resources spin up *only* when a room transitions from "stage" to "live broadcast." 
* **Egress Delivery**: While presenters interact in real time (&lt;200ms latency) across a distributed SFU cluster, attendee delivery is dynamically offloaded to low-latency HLS (LL-HLS) or WHEP edge networks. 

Because the backend cost is dictated by **egress gigabytes consumed per attendee minute**—not by the number of people authenticated with "Admin" rights—charging for host seats is no longer a technical necessity; it is purely an artificial monetization barrier.
